# Полный анализ работоспособности

Дата разбора: 2026-10-05.  
Метод: чтение текущего кода фронтенда и бэкенда. Приложение не запускалось, запросы к живой базе и браузерная проверка не делались. Ничего в коде по итогам этого разбора не менялось.

## Короткий вывод

Основные сценарии в коде замкнуты и могут работать, если подняты Postgres (`DATABASE_URL`) и переменные Supabase. Каталог, оформление заказа, редактор, просмотр заказов, админка смен, личный кабинет и QR-сканер связаны с одними и теми же таблицами.

Сдавать проект как закрытую систему рано. Данные сотрудников, заказов и паролей отдаются без авторизации. Вход на клиенте сравнивает пароль с уже скачанным списком пользователей. Скидка при оформлении заказа и скидка в редакторе считаются по-разному и при повторном сохранении расходятся. Время смены на сервере берётся из часов процесса, на Vercel это UTC, не Бишкек.

Вёрстка страниц заказов, каталога, админки и кабинета в целом собрана и имеет мобильные правила. Хрупкие места: ширина бокового меню задана в двух файлах, страница сканера без своих breakpoints, компонент подвала нигде не подключён.

## Как устроено

Фронтенд: React 19, react-scripts 5, React Router 7. Бэкенд: Express 5, PostgreSQL (`pg`), загрузка фото в Supabase Storage, JWT только для QR-отметки, Web Push.

Маршруты интерфейса:

| Путь | Кто по задумке | Что делает |
| --- | --- | --- |
| `/`, `/catalog` | все | каталог и калькулятор мебели |
| `/signin` | все | вход |
| `/order/:id` | все, страница публичная | карточка заказа и скачивание документов |
| `/cabinet` | любой вошедший | кабинет сотрудника: смены, график, объявления |
| `/view_orders` | любой вошедший | список заказов |
| `/admin` | только admin | сотрудники, смены, объявления |
| `/edit_mebel` | только admin | редактор каталога |
| `/placing_an_order` | только admin | новый заказ |
| `/order_editor/:id` | только admin | правка заказа и договора |
| `/scan` | admin и scanner, вне общего Layout | QR-отметка прихода и ухода |

Роли на клиенте проверяют `ProtectedRoute` и `AdminRoute` по объекту `currentUser` из `localStorage`. Сервер эти роли почти нигде не проверяет.

Коллекции API: `product`, `users`, `workSessions`, `order`, `announcements`. Общий CRUD в `collectionController.js`: чтение, создание, правка, удаление. Имена таблиц берутся из белого списка. Имена колонок сверяются с реальной таблицей, лишние поля запроса отбрасываются. Значения уходят параметрами, это не конкатенация SQL из текста пользователя.

## Бэкенд

### Что в коде работает

- Логин ищет пользователя по email, login или fullName и умеет и bcrypt, и старый открытый пароль.
- QR-отметка требует Bearer-токен и роль `scanner` или `admin`. Нет открытой смены со статусом `active` — смена начинается, есть — закрывается. Если конец раньше начала, к дате конца прибавляются сутки.
- Загрузка файла кладёт буфер в бакет `furniture` и возвращает публичный URL. Удаление вытаскивает имя файла из URL.
- Push: публичный VAPID-ключ, подписка, отписка, рассылка при объявлении. Таблица подписок создаётся и миграцией, и `CREATE TABLE IF NOT EXISTS` при старте.
- Поля договора в таблице `order` описаны миграцией `003_order_contract_fields.sql`.
- Замер времени ответа пишется в консоль. Порог 500 мс только подсвечивается, запрос не обрывается.

### Дыры, из-за которых система не закрыта

Критично.

1. CRUD коллекций не вызывает `authenticate`. Любой, кто знает адрес API, может прочитать и изменить пользователей, смены, заказы, товары и объявления. `GET /users` отдаёт строку целиком, вместе с полем `password`.
2. `POST /register` открыт. Пароль хэшируется, но в ответ уходит вся строка пользователя, включая хэш. Роль и остальные поля при регистрации не задаются.
3. Запасной секрет JWT в коде: `your-secret-key`, срок токена 1 час. Если в окружении секрет не задан, токены можно подписать этим значением.
4. Приватный VAPID-ключ записан в `pushService.js` как значение по умолчанию. `POST /push/test` шлёт уведомление всем подписчикам без проверки, кто вызвал метод.
5. `POST /upload` и `DELETE /upload` без авторизации. Multer держит файл в памяти и не ограничивает размер и тип. Большой запрос может занять память процесса.
6. `cors()` без списка доменов. С любого сайта можно дергать API из браузера жертвы, если та уже открыта. Для открытого CRUD это прямой доступ к данным, токен для этих маршрутов не нужен.

Серьёзно, но не «дыра наружу».

7. Сравнение с открытым паролем в `login` оставлено нарочно для старых записей. Пока такие строки есть, утечка таблицы `users` равна утечке паролей.
8. `GET /order` и `GET /order/:id` публичные. Карточка заказа на фронте тоже без входа. В заказе лежат ФИО, телефон, адрес и реквизиты.
9. Удаление пользователя не удаляет его смены. На клиенте список смен фильтруется только в памяти. В базе остаются строки `workSessions` на удалённый `userId`.
10. Удаление строки всегда отвечает `{ success: true }`, даже если id не существовал.
11. Новый товар без id получает `MAX(id) + 1` двумя запросами. Два одновременных создания могут взять один и тот же id.
12. На каждую запись сначала делается `SELECT * ... WHERE 1=0`, чтобы узнать колонки, и в лог пишутся имена колонок и ключи вставки. Это лишний запрос и шум, не поломка само по себе.
13. Часовой пояс сервера. QR собирает дату и время через `new Date()` на машине, где крутится Node. На Vercel это UTC. Для Бишкека отметки сдвинутся на 6 часов. Ручной старт смены в админке считает время в браузере администратора, QR считает время сервера. Два источника легко расходятся.
14. Колонки `endDate` в миграциях `workSessions` нет. Контроллер молча выкидывает поля, которых нет в таблице. Админка и кабинет показывают ночную смену как диапазон дат только если `endDate` реально сохранился. Длительность в минутах при этом пишется. Без живой схемы нельзя утверждать, что колонка отсутствует, но в репозитории её создания нет.
15. `express.json()` без лимита тела. Очень большой заказ упрётся в лимит по умолчанию и вернёт ошибку без понятного текста на фронте.
16. В корне бэкенда лежат `db.json`, `diag.js`, `fix_imgs.js`, `test2.js`, `test_front.js`. К рабочему серверу они не подключены. Их легко перепутать с боевым кодом.

Загрузка фото жива только если в окружении есть `SUPABASE_URL`, `SUPABASE_ANON_KEY` и бакет `furniture` пускает запись этим ключом. В коде это не проверяется до первого запроса. Локальные картинки из папки `uploads` отдаются как `/utilse`. Фронт в `resolveImageUrl` умеет и полный https, и `/utilse/`, и голое имя файла.

## Функции фронтенда

Общий контекст (`Context.js`) при старте и затем каждые 10 секунд скачивает `users`, `workSessions` и `product`. Это делает и гость на каталоге. Пароль при входе печатается в консоль браузера: `console.log('Попытка входа:', identifier, password)`.

Вход устроен в два слоя. Сначала пароль сравнивается в браузере с уже скачанным списком. Потом отдельно запрашивается `POST /login` ради JWT. Если второй запрос упал, пользователь всё равно считается вошедшим: в `localStorage` пишется `currentUser`, токена может не быть. Через час токен протухает, интерфейс об этом не знает. Сканер при ответе 401 сам разлогинивает. Остальные страницы токен в запросы не кладут, потому что CRUD его не требует. Поэтому заказы и админка «работают» и после протухания токена.

Сотрудник с ролью `scanner` по маршрутам может открыть кабинет и список заказов. Туда его пускает любая авторизация, не только admin. В кабинете он видит все смены всех людей: контекст не фильтрует выборку по текущему пользователю.

Автотестов сценариев в `frontend/src` нет. Папка `frontend/scripts` содержит разовые аудиты и сборку docx, это не регрессионный набор.

### Каталог

`useFurnitureCalculator` грузит `GET /product`, подставляет значения по умолчанию и считает формулы через `mathjs`. Ошибка сети показывается текстом, а не пустым экраном. Первый товар больше не открывается сам. Это рабочий контур, если API каталога отвечает.

Калькулятор и оформление заказа считают формулы независимо, каждый своим вызовом `mathjs`. Расхождение возможно, если в одном месте формула или округление обработаны иначе. Отдельной сверки результатов между страницами в коде нет.

### Вход

Форма вызывает `login` из контекста. Ошибки «не найден» и «неверный пароль» для пользователя схлопнуты в неуспех. Отдельного сообщения «сервер недоступен» при падении JWT нет: локальный вход может пройти, а сканер потом получит 401.

### Оформление заказа

Проверки перед сохранением: ФИО, телефон, хотя бы одна позиция. Надпись у адреса говорит «обязательно», функция `validateOrder` адрес не проверяет. Черновик проходит те же проверки, пустой черновик не сохранится.

Итог считается так: сумма позиций, затем процент `discountPercent`. В тело запроса уходят `subtotal` и `total`, и оба равны уже уменьшенной сумме. Сам процент в объект `order` не входит и на сервер не пишется.

Редактор считает иначе: сумма строк, минус `discountAmount`, плюс `taxAmount`. Заказ, созданный со скидкой в процентах, в редакторе имеет `discountAmount` равный нулю. Первое же сохранение в редакторе перезаписывает `total` полной суммой строк. Процентная скидка с оформления при этом пропадает.

Позиции уходят полем `product_order`. Локальное поле `positions` попадёт в JSON тоже, но сервер оставит его только если такая колонка есть.

Кнопки «из каталога» и «произвольная позиция» на узкой ширине больше не раздуваются по высоте: в колонке им сброшен `flex: 1 1 200px`. Это уже в стилях, отдельным багом сейчас не числится.

### Карточка заказа и редактор

Карточка читает заказ по id, рисует позиции из `product_order`, умеет скачать договор, КП и спецификацию на клиенте (`contractDocuments.js`, шаблоны docx). Сеть для самого файла документа не нужна. Если в заказе нет реквизитов, документ всё равно соберётся, пустые поля останутся пустыми. Это ограничение данных, не падение сборки.

Редактор сохраняет заказ целиком через `PUT /order/:id`, удаляет через `DELETE`. Ошибка HTTP показывается тостом. Оптимистичного отката нет: при ошибке локальное состояние уже могло измениться до ответа только у позиций в памяти до нажатия «сохранить». Само сохранение ждёт ответ.

Финансы редактора и финансы формы оформления не одна модель. Это главный функциональный разрыв заказов.

### Просмотр заказов

Список берётся отдельным запросом, не из общего контекста. Фильтры, сортировка и карточки завязаны на поля заказа. Если API недоступен, есть ветка ошибки. Публичность данных здесь такая же, как у `GET /order`: страница закрыта маршрутом, API нет.

### Редактор мебели

Загрузка списка, создание, правка формул, загрузка и удаление фото через `/upload`. Ошибки тостами есть. Гонка `MAX(id)+1` на бэкенде относится и сюда. Пока создают по одному, id не столкнутся.

### Админка

Сотрудники: создание с хэшем пароля на клиенте (`bcryptjs` в браузере), правка, удаление, запрет удалить себя. Смены: ручной старт, закрытие, правка длительности, в том числе через полночь по полю `endDate`. Объявления: создание, включение, удаление, push. Если колонки `endDate` в базе нет, правка ночной смены сохранит минуты и время конца, а дату конца интерфейс после обновления страницы потеряет.

Кнопки таблицы на узкой ширине уменьшены по шрифту и отступам, не растянуты на сотни пикселей.

### Кабинет

Читает тех же пользователей и смены из контекста. Фильтры периода, график, экспорт PDF, баннер push. Баннер на ширине до 600px больше не занимает 220px пустой высоты: у текста в колонке сброшен `flex-basis`. Объявления подгружаются отдельно. Кабинет не ограничивает данные текущим сотрудником.

### Сканер

Камера через `html5-qrcode`, ручной ввод badge id, пауза камеры на время запроса, защита от двойного скана флагом `processing`. Успех пишет `localStorage['qr-update']`, другие вкладки по этому ключу сразу дергают обновление. 401 через 3 секунды выходит из аккаунта. Без токена запрос уходит с `Authorization: Bearer null` и сервер ответит 401. Это ожидаемо, если вход не получил JWT.

Страница сканера не внутри `Layout`: бокового меню там нет, шапка приложения тоже.

### Общие куски интерфейса

Тосты и подтверждение вынесены в контекст, страницы ими пользуются. Тема каталога хранится в `localStorage`. Сервис-воркер регистрируется в production и на localhost. Фото-слот и спиннер переиспользуются. Подвал `Layout/Footer/footer.js` нигде не импортируется. На страницах его нет.

## Стили и вёрстка

Общая сетка: сверху 64px под шапку, слева 256px под меню (`App.scss`, класс `.main`). Меню фиксировано, ширина 256px (`header.scss`). Мобильная шапка включается и в CSS, и в JS по одной границе `max-width: 650px`. Ниже неё десктопное меню скрывается (`header_PC`), у `.main` обнуляется левый отступ (`all_adaptation.scss`). Эти два файла подключаются так, что адаптация идёт после базовых стилей, поэтому на телефоне пустая колонка слева не остаётся.

Между 651px и 900px `all_adaptation.scss` сужает и меню, и отступ контента до 200px, кнопки меню до 180px. Базовые стили меню при этом говорят 256px и 223px. Сейчас побеждает адаптация, числа сходятся. Правка только одного файла снова разъедет меню и контент. Пустой блок `@media (max-width: 955px)` в том же файле ничего не делает. Правило `.input-row input { width: 150px / 180px / 200px }` на очень узких ширинах выглядит как след старой формы, не как сетка текущих страниц.

Страницы заказов, каталога, админки, кабинета и редактора мебели имеют свои `@media`. Поля в модалках на телефоне получают `font-size: 16px`, чтобы iOS не увеличивал страницу при фокусе. Кнопки в колонке, у которых раньше был `flex: 1 1 Npx`, проверены:

| Место | Состояние |
| --- | --- |
| Оформление заказа, две кнопки добавления позиции | сброшено, высота по тексту |
| Карточка заказа, кнопки документов | в колонке уже `flex: none` |
| Модалка админки, кнопки действий | в колонке `flex: 1 1 auto` |
| Объявления, кнопки карточки | в колонке `flex: 1 1 auto` |
| Заголовок блока объявлений | было 200px высоты, в стилях уже сброшено |
| Баннер push в кабинете | было 220px, в стилях уже сброшено |
| Статистика списка заказов, `flex: 1 1 480px` | только от 1100px и только в ряд, высоту не ломает |

Намеренная высота 40–48px у кнопок на телефоне оставлена: это зона нажатия, не раздутый блок.

Сканер (`scan.scss`) своих media-query не имеет. Рамка камеры 280×280 при боковых полях 24px на экране 320px почти упирается в край. Часы 64px на узком экране могут не влезть в одну строку без сжатия. Ручной ввод и кнопка стоят в один ряд без переноса. Это самый слабый адаптив в проекте.

Каталог: на ширине до 640px карточка списка становится колонкой, модалка прижимается к низу экрана, кнопка расчёта на всю ширину и не ниже 48px. Для главной кнопки это нормально.

Редактор заказа до 820px складывает три колонки в одну, левая колонка ограничена 42vh. Длинный список позиций на телефоне придётся скроллить внутри блока, страница при этом не заперта по высоте окна.

Админская таблица смен на узкой ширине получает горизонтальный скролл и `min-width` строки около 540px. Так таблица не ломает страницу, но на телефоне читается только жестом в сторону. Это компромисс, не ошибка высоты кнопок.

Светлая и тёмная темы завязаны на токены в `styles/` и модификаторы `*-theme-light` на страницах. Шапка смотрит ещё и на `prefers-color-scheme`. Если системная схема и переключатель темы расходятся, шапка и контент страницы могут быть в разных режимах. Имеет смысл глазами сверить шапку и каталог в обеих темах. По одному только коду это не подтверждено как всегда видимый баг.

`footer.scss` подключается только из неиспользуемого компонента. На экран не влияет.

Зависимости `sass` и `scss` стоят вместе. Стили компилирует `sass`. Пакет `scss` к вёрстке страниц не нужен.

## Что можно считать рабочим контуром

Если база и Supabase настроены, по коду проходят такие цепочки:

- гость открывает каталог, выбирает мебель, считает размеры;
- администратор входит, создаёт заказ с позицией из каталога или произвольной, открывает карточку, скачивает документ;
- администратор правит заказ, статус, реквизиты договора и сохраняет;
- администратор ведёт сотрудников и смены, сотрудник в кабинете видит те же смены и может выгрузить PDF;
- сканер с валидным токеном отмечает приход и уход, админка подхватывает смену по опросу или по событию другой вкладки;
- фото товара уходит в Supabase, в карточке показывается публичная ссылка.

Это описание связей в коде, не протокол прогона.

## Что мешает сдаче, по порядку

1. Открытый CRUD и выдача паролей на любой `GET /users`, плюс клиент, который эти пароли скачивает и пишет вводимый пароль в консоль.
2. Открытые регистрация, загрузка файлов и тестовый push. Секреты JWT и VAPID лежат в репозитории как значения по умолчанию.
3. Скидка процентом на оформлении не сохраняется и затирается в редакторе.
4. Время QR и, возможно, дата конца ночной смены зависят от схемы базы и часового пояса сервера.
5. Сканер и роли: интерфейс пускает scanner в кабинет и заказы, сервер роли почти не смотрит. Сессия в `localStorage` живёт дольше JWT.
6. Вёрстка сканера без мобильных правил и двойное описание ширины меню в `header.scss` и `all_adaptation.scss`.

Исправления в этом разборе не делались.
